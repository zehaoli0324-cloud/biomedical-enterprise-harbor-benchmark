# Benchmark 设计草案

## 任务单元

每个任务至少包含：

```text
task/
├── task.yaml              # 目标、约束、输入输出和风险级别
├── instruction.md         # 给 agent 的任务说明
├── environment/           # 固定依赖、工具和数据
├── tests/                 # verifier 与参考答案
├── expected_artifacts.md  # 允许的中间产物和必需证据
└── trials/                # prompt、trajectory、output、score
```

## 任务层级

### L0：单环节正确性

例如读取实验表、识别重复层级、核对 DOI、解释一个图、检查单位换算。

### L1：短流程执行

例如从输入矩阵完成质量控制和一个统计分析，要求保存日志、参数和结果表。

### L2：多工具流程

例如从文献检索到数据下载、预处理、分析和结果解释，要求处理一个工具失败或输入变化。

### L3：研究级闭环

例如从问题定义、假设、实验设计、分析、图表到结论边界，必须同时满足科学、工程和证据约束。

## 评分维度

不要只用一个最终 reward。建议保存以下分数：

| 维度 | 说明 |
| --- | --- |
| 科学正确性 | 研究问题、实验单位、模型、解释是否正确 |
| 结果准确性 | 数值、标签、文件和图表是否匹配参考结果 |
| 证据完整性 | 每个关键主张是否能追溯到数据或来源 |
| 工程可复现性 | 环境、参数、随机性和中间产物是否足以重跑 |
| 工具编排 | 工具选择、顺序、参数和错误恢复是否合理 |
| 交付合规性 | 是否生成规定文件、字段、目录和报告 |
| 不确定性与安全 | 是否在证据不足或高风险时暂停、澄清或降级 |

## 失败注入

为了防止模型只记住固定流程，任务应支持可控变体：

- 改变列名、文件名、物种、单位或实验条件。
- 删除一个关键对照或引入一个不可分析的组合。
- 把工具版本、路径或依赖改成轻微不兼容。
- 注入空文件、部分下载、重复样本、批次混淆和异常值。
- 给出两个都合理但科学含义不同的分析模型。
- 修改一个图或表中的数字，测试端到端一致性审计。

## 轨迹记录

每次 trial 应保存：

- 原始 prompt 和完整工具调用序列。
- 每一步的输入、输出、退出码和环境状态。
- agent 的最终提交文件和 verifier 输出。
- 模型是否主动发现错误、请求澄清或承认不确定性。
- token、时间、成本、CPU、内存和网络使用。

## 首批任务优先级

第一批建议从以下场景开始，因为它们既有现实风险，也能做程序化评分：

1. 单细胞/组学分析中的实验单位和重复层级判断。
2. 文献检索、引用核验和证据表构建。
3. 论文图表、方法和结果段的一致性审计。
4. 蛋白结构预测、对接和序列设计的工具边界判断。
5. 实验设计、样本量和对照选择。
6. 代码环境修复和独立重跑。
7. 基因编辑候选设计与脱靶风险报告。
8. 从选题到实验、分析和论文的长程闭环。
