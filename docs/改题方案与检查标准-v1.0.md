### 改动 10/11 的实现要点

判定"是否把某输入当作证据"，不能在自由文本里扫字符窗口。本批两次踩坑：

1. 窗口 160 字符时，**前一句的否定词**（如"This audit does not authorize wet-lab action"）
   会掩盖后一句的真实引用；
2. 收紧到"只看提及之前"后，**排除语常位于提及之后**（"…are calibration fixtures.
   They are excluded and are NOT cited as evidence."），正向提交反被判错。

最终采用**段落作用域**：按空行分段，段内出现该文件名且段内无排除标记词才算"当作证据"。
这一条同时满足正反双向探针，且不依赖句子切分或窗口参数。

反向检查（`retain`、`validated`）同理：只看该词**之前 12 个 token** 内是否有否定词，
避免"not validated"被当成"validated"。

Dockerfile 可移植化的实测数据：单题 `--no-cache` 全量构建耗时 **4 分 00 秒**
（`python:3.11-slim` + apt 装 curl/bash/nodejs/npm/procps/ca-certificates + npm 装
`@anthropic-ai/claude-code`，各带 5 次重试）。这同时消除了 checklist 记录的
`AgentSetupTimeoutError`（旧方案在容器内现装实测 452 秒，超过 360 秒默认超时）。

## 一、可迁移的问题防治方案

以下每条都来自本批题的实测故障，不是推测。每条给出：症状 → 根因 → 通用改法 →
验收口径。按此顺序可复用到任何新题。

### P1　评分器副本漂移

**症状**　题目根有 `verifier.py`，`tests/` 下另有一份。两份逻辑不同，而 harbor 的
`tests/Dockerfile` 是 `COPY . /tests/`，实际运行的是 `tests/` 那份。根副本改了、
`tests/` 没改时，修改完全不生效；反向改则可能覆盖掉正确逻辑。

**根因**　缺少单一规范来源。方案 §1.3-5 已明确要求评分器只能有一处定义。

**通用改法**

1. 认定 `tests/verifier.py` 为唯一运行副本（由 `tests/Dockerfile` 的 `COPY . /tests/` 决定）。
2. 改任何评分逻辑，只改这一份。
3. 根副本用 `cp tests/verifier.py verifier.py` 单向同步，禁止反向手改。
4. 更彻底的做法是删除根副本，只保留 `tests/` 一份；若外部工具链依赖根副本，则必须在
   CI 中断言两者字节一致。

**验收口径**

```bash
for d in */; do t=${d%/}; [ -f "$t/verifier.py" ] && [ -f "$t/tests/verifier.py" ] && \
  { cmp -s "$t/verifier.py" "$t/tests/verifier.py" || echo "DRIFT: $t"; }; done
# 期望：无输出
```

### P2　隐藏取值陷阱

**症状**　模型的科学判断完全正确，但 verifier 要求精确字符串（状态枚举、大小写、
路径前缀、小数位数），而这些取值只存在于 verifier 侧的隐藏标签文件。任何 agent
拿不到分，除非碰巧猜中拼写。

**根因**　把"协议拼写"与"科学结论"混为一谈。前者本来就应该公开，后者不能公开。

**通用改法**　按**该字符串编码的是什么**分两类，而不是按题目分：

| 类型 | 例子 | 处理 |
|---|---|---|
| 协议拼写 | `stop_and_escalate`、`metadata_only`、`UNAVAILABLE`、`donor`、`off` | 公开写入 instruction 的"受控取值"段 |
| 科学结论 | 哪些范围是观察到的、哪些主张必须阻断、下一步证据要求是什么 | 放宽 verifier，不公开 |

公开拼写**不会送分**：判分矩阵把不同分支映射到不同取值，知道拼写不等于知道该用哪个。
本批的 `glycan` 就是范本 —— `action` 必须是 `stop_and_escalate`，而"GP-002 的主张不
成立、需要升级"这个判断仍要模型自己做。

**放宽后必须双向测试**：改写措辞但科学等价 → 通过；漏掉任一必需概念或越界声称 → 仍失败。

**验收口径**

```bash
# 扫描参与比较的字面量，检查是否在 agent 可见文本中出现
# 完整脚本见第三节 1.7
# 期望：剩余项全部是字段名、前缀、参数名等虚警，无真实"必须取值"
```

### P3　字符串精确比较惩罚正确披露

**症状**　verifier 用 `"guide_counts.tsv" not in report` 判断"是否把已排除的校准
文件当证据引用"。而模型在报告里**正确地披露**"这些文件已排除"时，文件名出现，
反被判错。

**根因**　子串存在性检查无法区分"引用为证据"与"声明为排除"。

**本批已采用的做法（改动 10/11，实测通过）**

按**段落作用域**判定：把报告按空行切成段，某段内出现该文件名、且该段内不含任何排除
标记词（`not`/`exclude`/`omitted`/`defer`/`unavailable` 等），才算"当作证据引用"。

另外三个选项（保留备查）：

1. 只在结构化列里查（如 `source_inventory.tsv` 的 `evidence_role` 列），不查自由文本。
   本批的 `source_inventory.tsv` 实际**没有**被 verifier 用来做这项判定，故未采用。
2. 要求模型用特定措辞声明排除，并只在该小节内做反向检查 —— 对模型约束过强。
3. 语义检查 —— 与本批采用的段落作用域方案等价，但需额外依赖句子切分。

**为什么不能用字符窗口**（本批踩过两次）

- 窗口 160 字符：**前一句的否定词**（"This audit does not authorize wet-lab action"）
  掩盖了后一句的真实引用，负向提交被误判为合规。
- 改为"只看提及之前"：**排除语常位于提及之后**（"…are calibration fixtures. They are
  excluded and are NOT cited as evidence."），正向提交反被判错。

段落作用域同时满足正反两个探针，且不依赖句子切分或窗口参数。

**验收口径**　构造两份提交：一份把文件当证据、一份正确声明排除。前者必须失败，
后者必须通过。只测前者会漏掉这个 bug。

### P4　可移植性：本机私有基础镜像

**症状**　`environment/Dockerfile` 写了 `FROM fable-base:local`。本机能跑，换机器或
清理 Docker 缓存后无法构建。

**根因**　为规避容器内安装超时，把 node + claude-code 预烤进本地镜像，并把
`FROM` 改成本地标签。这是**本机运行时优化**，不能进发布包。

**通用改法**

1. 发布包的 `environment/Dockerfile` 必须 `FROM` 公开可拉取且版本固定的镜像。
2. 需要预装依赖时，把安装步骤**内联**进 Dockerfile，并加带重试的循环：

```dockerfile
FROM python:3.11-slim
RUN for i in 1 2 3 4 5; do apt-get update && apt-get install -y --no-install-recommends \
      curl bash nodejs npm procps ca-certificates && break; sleep 15; done
RUN for i in 1 2 3 4 5; do npm install -g @anthropic-ai/claude-code && break; sleep 15; done
RUN command -v claude && claude --version
```

3. 本机调试用的本地镜像版本单独维护，不进发布包。

**验收口径**

```bash
grep -H '^FROM' */environment/Dockerfile | grep -vE 'python:3\.11-slim|<公开镜像>:<固定版本>'
# 期望：无输出
```

### P5　产物未声明

**症状**　oracle 返回 0.0，但 verifier 逻辑正确。原因是 separate verifier 模式下，
只有 `task.toml` 的 `artifacts` 声明过的文件才会传入判分容器。

**根因**　`artifacts` 与 verifier 实际读取的文件集合不一致。

**通用改法**　从 verifier 源码反推它读取的每个文件名，与 `artifacts` 做差集，
差集必须为空。注意 verifier 可能用 `/app/output`、`/root/results` 等不同前缀。

**验收口径**　见第三节 1.6。差集非空即阻断。

### P6　路径与格式归一化

**症状**　模型写 `data/counts.tsv`，verifier 要 `counts.tsv`；模型写
`biological_replicate (BBBC021 ...)`，verifier 要裸名；模型写 `yes (metadata)`，
verifier 要 `true`。语义都对，格式都挂。

**根因**　比较前未归一化。

**通用改法**　凡比较用户可控的字符串，统一先做：

- 路径：`Path(name).name` 取 basename，必要时同时尝试无前缀回退
- 大小写：`.strip().upper()` 或 `.strip().lower()`
- 枚举：接受同义集合而非单一字面量
- 数值：`math.isclose(..., abs_tol)` 的容差必须与数据精度匹配（见 P7）

**验收口径**　对每个归一化点构造"语义相同、格式不同"的提交，必须通过。

### P7　数值容差与数据精度不匹配

**症状**　verifier 用 `abs_tol=1e-9` 比较均值，而均值是循环小数（如 `1291/30`）。
模型写 4 位、6 位、8 位小数**都挂**，只有 Python `repr` 级精度能过。

**根因**　容差按"浮点相等"设定，没有按"任务允许的提交精度"设定。

**通用改法**

1. 容差必须从题目允许的精度反推。若 instruction 未规定精度，容差应取"合理人工报告
   精度的上界"，通常 `1e-3`。
2. 有区分度的容差必须同时保证**仍能拒绝真实错误**：本批已验证 `1e-3` 下"分子差 1 /
   分母差 1 个 cell"仍全部失败。
3. 循环小数必须在 instruction 里明确精度要求，或改成比较整数分量。

**验收口径**　构造三份提交：正确值（通过）、精度内近似（通过）、真实错误（失败）。

### P8　运行前置条件：模型侧拒答与网关超时

**症状**　agent 在第 1 轮、零工具调用时失败，产物为空。错误为
`API Error: ... Details: [bio]` 或网关 `524`。

**根因**　与题目质量无关：

- `[bio]` 是模型侧策略对题面文本的拦截。crispr-resistance（guide 设计 + 人类基因编辑
  验证）与 l1000（药物 MoA 推断，不涉编辑）都被拦；同为 CRISPR 的 crispr-screen
  （措辞为"审计已发表的 screen 命中"）未被拦。
- `524` 是网关 120s 硬顶，长推理被掐。

**通用改法**

1. 这两类必须记为 `EXECUTION_FAILED`，reward 为 `null` 而非 `0`，**不得进入模型
   失败统计**。
2. 拒答题的处理见第五节 D3（换措辞 / 单列不可用 / 换模型）。
3. 网关超时的处理见第五节 D4（服务端放宽 / 降 reasoning effort）。

**验收口径**　`result.json` 中 `exception_type` 非空的 trial，一律排除出科学统计。

### P9　`-p` 静默覆盖

**症状**　`harbor run -p A -p B -p C` 不报错、不警告，实际只跑 C。

**根因**　`-p` 只接受一个路径。

**通用改法**　多任务必须走 job-config YAML，且启动前门控 task 数。

**验收口径**


| 步 | 动作 | 产物 | 门禁 |
|---|---|---|---|
| 1 | 设计与复算：定义主决策、分析单位、可见证据、参考答案 | `candidate_design.json` | 科学问题可答、答案边界明确 |

### 阶段 2　动态检查（必须启动容器）

每题按顺序跑完五项：

| # | 检验 | 命令 | 期望 | 抓住什么 |
|---|---|---|---|---|
| 2.1 | 参考解 | `harbor run -p <task> -a oracle` | **1.0** | 题目可解、产出路径正确、verifier 能拿到产物 |
| 2.2 | 空解 | `harbor run -p <task> -a nop` | **0.0** | **最高价值**：唯一能抓出 verifier 自评分的检查 |
| 2.3 | 删除一个必需产物 | 见下 | 失败 | verifier 确实在读取产物 |
| 2.4 | 篡改一个关键字段 | 见下 | 失败 | 不是只检查文件存在 |
| 2.5 | 改写措辞但科学等价 | 见下 | **通过** | 仅在放宽过 verifier 后需要，防止放宽过度 |

**为什么 2.2 不可省略**：本批曾有 4 题 oracle 全部返回 1.0、外观完全健康，正是 nop
也返回 1.0 才暴露出 verifier 在给自己打分。只跑 oracle 会让这些题带着致命缺陷进入
正式评测。

**2.3 / 2.4 的构造**：复制题目到临时目录，让 `solve.sh` 在产出后删除一个必需产物
（或篡改一个关键字段），再跑 oracle 并要求失败。这样复用 harbor 自身的接线，不必
猜测每个 verifier 的调用签名和数据路径。

**2.5 的构造**：对每个放宽点，构造"语义等价、措辞不同"的提交，要求与参考解同样通过。

**成对验证与读取真实 reward**

```bash
python3 - <<'PY'
import json, glob
def reward(job):
    fs = glob.glob(f"jobs/{job}/*/result.json")
    if not fs: return "NO-RUN"
    d = json.load(open(fs[0]))
    r = ((d.get("verifier_result") or {}).get("rewards") or {}).get("reward")
    return r if r is not None else "EXC:" + str((d.get("exception_info") or {}).get("exception_type", "?"))
for t in sorted(p.split("/")[0] for p in glob.glob("*/task.toml")):
    o, n = reward(f"chk-ora-{t}"), reward(f"chk-nop-{t}")
    print(f"{t:46s} oracle={o!s:6s} nop={n!s:6s} {'PASS' if (o == 1.0 and n == 0.0) else '*** FAIL'}")
PY
```

> **reward 必须从 `result.json` 读取，不要解析终端表格。**
> 路径：`jobs/<job>/<trial>/result.json` → `verifier_result.rewards.reward`。
> 解析终端输出踩过两次坑：`tr -d '│ '` 会把 reward `1.0` 与计数列 `1` 粘成 `1.01`；
> awk 取字段会命中 Trials 行而非 Reward 行。两次都产生过虚假的 FAIL。

## 四、运行真实 agent trial 的前置条件

### 4.1　会导致立刻失败的

**① model slug 的形式**

harbor 的 claude-code adapter 把 `-m` 的值**原样注入容器环境**
（`agents/installed/claude_code.py`：`command.append(f"ANTHROPIC_MODEL={model}")`）。
因此该值必须是 Anthropic API 认可的模型 ID，**不能带 provider 前缀**：

```bash
-m claude-fable-5-1              # 正确
-m anthropic/claude-fable-5-1    # 错误，会被原样传成 ANTHROPIC_MODEL=anthropic/...
```

`--print-config` **不做校验**，只原样回显你给的字符串。真正的验证只能靠实际运行，
观察是否出现 `ModelNotFoundError`。

**② agent 阶段必须联网**

```toml
[environment]
network_mode = "public"          # agent 阶段

[verifier.environment]
network_mode = "no-network"      # verifier 阶段，与上面互不影响
```

**③ 凭证二选一，不要混用**

```bash
# 路线 A：订阅（Claude Pro/Max）
claude setup-token                       # 交互式，需浏览器
unset ANTHROPIC_API_KEY                  # 关键：两者都在时 CLI 优先用 API key
export CLAUDE_CODE_OAUTH_TOKEN=$(cat ~/.claude/harbor-oauth-token)

# 路线 B：API key
export ANTHROPIC_API_KEY=<key>
```

**不要用 `--ae` 传递含 `AUTH`/`TOKEN`/`KEY` 的变量**：harbor 将这类变量视为 secret，
持久化 trial config 时会脱敏或模板化，传入容器的值与预期不符。通过环境变量传递可
避免它落入 `argv` 与 `config.json`。

**④ 先冒烟 1 题再全量铺开**

镜像构建与凭证是最易出错的两个环节。优先选择 verifier 未被修改过、不可发现取值为零
的题目，信号最干净。

**⑤ `-p` 只接受一个路径**（见 P9）

**⑥ agent 安装阶段是最脆弱的一步**（见 P4）

### 4.2　会导致误判结果的

**⑦ 订阅有速率限制。** 长 trial 可能中途停滞或断开。trial 结束异常时先查
rate-limit 消息，再怀疑题目。批量评测应使用 API key。

**⑧ 模型侧拒答与网关超时必须单列。** 见 P8。带 `exception_type` 的 trial 一律
排除出科学统计，reward 记 `null` 而非 `0`。

**⑨ 修改过难度构成的题目与旧 baseline 不可比。** 公开协议词表、放宽措辞比较之后，
之前的失败可能仅仅是没猜中拼写。这正是修改目的，但历史对比数据失效。

**⑩ 格式型 verifier 的高分含义有限。** 只检查产物完整性、来源指纹与"克制不越界"
纪律的 verifier，不判定算出来的科学结果是否正确。

**⑪ 跑完必须做轨迹分析。** agent 失败不等于题目难 —— 也可能是 instruction 欠说明、
环境损坏，或 verifier 拒绝了正确答案：

```bash
harbor analyze -r rubrics/trial-analysis.toml -m <强模型> jobs/<job-name>
```

默认 judge 是 haiku-4-5，不足以判断"科学 verifier 是否公平"，必须显式传 `-m`。
注意 `harbor analyze` 与 `harbor check` 直接调用模型、不走 CLI，**需要 API key**。

## 五、需人工决定的事项

以下五条属任务设计判断，不能自动化，也不应默认处理。

**D1　子串检查如何改**（对应 P3）—— **已解决，2026-09-23**

原问题：crispr-screen 的 `"guide_counts.tsv" not in report` 与 md-replica 的同类检查
惩罚"正确披露已排除"。**已按段落作用域实现**（详见 P3 与改动 10/11），并双向验证：

| 探针 | 结果 |
|---|---|
| crispr-screen 正确披露排除 | PASS（修复前为 FAIL） |
| crispr-screen 当作证据引用 | FAIL（正确拒绝） |
| md-replica 同上（单元级，端到端无法触发） | 5/5 用例全部符合预期 |
| microscopy `do not retain…` | PASS（修复前为 FAIL） |
| microscopy `retain image-level claims` | FAIL（正确拒绝） |
| perturbseq `not validated` | PASS（修复前为 FAIL） |
| perturbseq `were validated` | FAIL（正确拒绝） |

遗留说明：md-replica 的该检查**在真实提交上恒为不触发**，因为判定读取的是
`submission.json`，而真实提交中 `calibration` 出现 0 次。该检查应视为防御性代码，
其有效性只能用合成输入验证 —— 这一点已如实记录，不得声称"端到端验证通过"。

**D2　md-replica 的 replay 格子**
`(present, original)` 情境下，模型写 `changed_claims=none`（"冲突存在但未修复，
所以主张未变"），verifier 要 `bounded_trajectory_subset`（"冲突存在即应指出需要的
修复"）。两种读法都成立，是本批**唯一一条真实的判断分歧**，需领域专家裁定。

**D3　被拒答的两题**
crispr-resistance 与 l1000 连续 3/3 拒答。选项：调整题面措辞（对照 crispr-screen
的可用措辞）、单列为"模型不可用"、或换模型跑这两题。

**D4　网关 120s 硬顶**
experimental-design 三次里 1 次撞上。选项：请服务端放宽，或对深度推理题设
`--ak reasoning_effort=medium`。

**D5　科学审阅**
十题目前全部为 `"scientific_review": "PENDING"`，且无 `scientific_review.json`
文件。正式难度统计前必须有独立审阅者签核。本文件不能替代科学审阅结论。

## 六、发布门禁速查

任一项失败即不得进入正式 trial 或对外发布：

| 门禁 | 必须满足 |
|---|---|
| 可启动 | `task.toml` 存在；`environment/` 可独立作为 build context 构建 |
| 构建复现 | 无本机私有镜像；依赖在 build 时固定安装 |

## 八、`pretrial-gate.sh`：一条命令跑完静态与契约门禁

路径：`~/Desktop/pretrial-gate.sh`（`chmod +x` 已设）。

```bash
./pretrial-gate.sh <tasks_dir> [repo_dir] [--with-harbor]
# 例
./pretrial-gate.sh ~/Desktop/ten-task-science-benchmark-20260922/tasks
```

**设计原则**

- 只读题目文件，不自动修复，不写题目目录。
- **「不适用」与「失败」分开计**：工厂格式的门禁在 Harbor 原生题上记 `N/A`，不记 `FAIL`。
- 需容器与凭证的动作（oracle/nop）默认**只打印命令**，加 `--with-harbor` 才真跑。
- 结果同时落 JSON（`/tmp/pretrial-gate-<时间戳>/result.json`），便于归档比对。

**它跑什么**

| 段 | 内容 | 依据 |
|---|---|---|
| A1–A9 | 结构与必备文件、答案隔离、instruction 副本、后缀=timeout、语法、`artifacts` 覆盖、可发现取值扫描、`FROM` 可移植性、评分器副本一致性 | 第三节 1.1–1.9 |
| B1 | `check_candidate_sop_contract.py`（候选级契约） | SOP §9 |
| B2 | `check_pretrial_matrix.py`（控制矩阵，逐题） | SOP §9.1 |
| B3 | `check_difficulty_modules.py`（难度模块，逐题）—— 通过 `/tmp` 两层布局桥接真跑 | 第四节 |
| B7 | `check_real_data_literature_gate.py`（真实数据与文献，逐题） | SOP §2/§8 |
| B8/B9 | 仓库级门禁（判定对象是工厂自身包，默认 `N/A`；`WITH_REPO_GATES=1` 才跑） | — |
| B10 | `check_harbor_trial_preflight.py` —— 未给 `HARBOR_TRIAL_CONFIG` 时自动从题目目录生成 config；仅 `task_shape` 阻断时归为「布局不适用」 | SOP §10.1 |
| C1 | `--with-harbor` 时逐题真跑 oracle/nop（`-o` 落到 `/tmp`，不污染发布包），reward 从 `result.json` 读 | 第三节阶段 2 |
| C2 | `check_harbor_trial_results.py` 审计 jobs 目录，把执行失败/采集失败与模型失败分开 | SOP §10.1 |

**退出码**：`0` = 全部适用门禁通过；`1` = 有失败；`2` = 用法错误。

**环境变量**

```text
DIFFICULTY_MANIFEST   覆盖难度模块 manifest 路径
WITH_REPO_GATES=1     跑 B8/B9 仓库级门禁
HARBOR_TRIAL_CONFIG   指向 harbor trial config.json，启用 B10
```

**三个必须知道的实现约束**（本批踩到）

1. `check_difficulty_modules.py` 取 `package.parent.name` 作 `task_id`、`package.name` 作
   `version`，且对路径 `resolve()`。因此扁平布局 `tasks/<task>/` 直接跑必报
   `parse_error:KeyError:'tasks'`，**且不能用 symlink 桥接**（会被 resolve 穿透）。脚本的做法是
   在 `/tmp` 造 `task_packages/<task_id>/<version>/author_private/` 并**只拷贝**它读取的那一个
   文件 `difficulty_modules.json`（`version` 取自该文件字段，十题均为 `0.1.0-development`）。
2. `check_harbor_trial_preflight.py` 的 `REQUIRED_TASK_FILES` 含 `solver/query.md`、
   `solver/output_contract.json`、`judge_private/verifier/verifier.py` —— 这是工厂布局，Harbor
   原生题必然触发 `task_<i>_shape`。脚本把「blockers 全为 shape」归为 `N/A` 并附上其余通过项数；
   出现任何非 shape 阻断才计 FAIL。
3. `$VAR` 后紧跟中文标点时，bash 会把多字节字符并入变量名。脚本内所有此类位置均已改为 `${VAR}`。

## 十二、2026-09-24 v12 复验新增硬性检查标准

本节把本轮十题 v12 打包、解包和 pretrial 复验中实际遇到的问题固化为发布前检查。
这些检查适用于扁平 Harbor 包（`tasks/<task>/`）和题库源目录。历史审计记录保留原样，
本节是后续包的 fail-closed 增量门禁。

### 12.1 每题必须有任务描述、难度说明和验证说明

每个任务的 `README.md` 必须包含以下四个独立小节，标题必须逐字匹配：

```text
## Task description
## Difficulty
## Reference solution
## Verification
```

`[metadata]` 中还必须有非空的 `difficulty_explanation`、
`solution_explanation`、`verification_explanation`。检查不能只看字段存在：

- `Task description` 必须写清研究目标、输入文件、输出目录、文件格式和失败时的报告方式；
- `Difficulty` 必须指出真实的科学瓶颈、证据边界或决策分支，不能只写文件数量、耗时或
  “步骤多”；
- `Reference solution` 必须说明 oracle 生成什么以及它不代表什么；
- `Verification` 必须说明 verifier 读取哪些产物、如何判定成功、哪些错误必须得 0 分。

`instruction.md` 的输入、输出和 verifier 约束必须与 README 一致。若 verifier 要求某个
列的字面枚举、固定行数或精确键名，instruction 必须公开该枚举、映射和行数，不能只写
“覆盖全部”“包含相关信息”。任务描述应覆盖行为、输入、输出和验证要求，参照
<https://github.com/harbor-framework/terminal-bench-science/pull/567> 的验收口径。

建议的批量检查：

```bash
for task in tasks/*; do
  test -f "$task/README.md" && \
  for h in 'Task description' 'Difficulty' 'Reference solution' 'Verification'; do
    rg -q "^## ${h}$" "$task/README.md" || exit 1
  done
done
```

缺少任一小节、只写格式难度、或 README 与实际 verifier 不一致，均为 `FAIL`。

### 12.2 扁平包必须直接检查每题 SOP 卡片

扁平包的结构通常是 `tasks/<task>/`，工厂目录检查器按
`task_packages/*/<version>/` 搜索时可能找不到题目，不能把“未发现任务”当作通过。
必须对每个 `tasks/<task>/author_private/sop_card.json` 直接检查：

- 文件存在，JSON 可解析；
- `schema_version`、`task_id`、`scenario_matrix`、`release_permitted` 存在；
- `scenario_matrix` 恰好包含 `clean`、`replay`、`mutation`、`offline`、`packaging`；
- `release_permitted` 必须为 `false`，直到科学审阅和动态门禁均通过；
- 卡片中的数据、网络、答案隔离和 verifier 状态与题包实际文件一致。

仓库中的 `scripts/check_flat_task_sop_cards.py` 是扁平包的标准检查器。运行时必须报告
题目数、卡片数、缺失字段和失败题目；卡片数不等于题目数时直接阻断。

### 12.3 冻结回放路径必须在临时题包中可解析

`data/transformation_manifest.json` 中的 `derivation_script` 必须是题包内的相对路径，
并能从复制后的临时包解析。禁止使用只在源仓库存在的
`tasks/<task>/...` 绝对或前缀路径。回放检查必须同时验证：

1. 脚本存在且不联网下载；
2. 生成文件的相对路径、字节数和 SHA-256 与 manifest 一致；
3. `data/freeze_manifest.json` 与 `data/release_input_manifest.json` 中的路径和哈希一致；
4. 运行结果为 `PASS`，而不是“脚本存在”或“目录存在”。

必须在复制到临时目录后运行 `scripts/replay_real_candidate_artifacts.py`，不能只在源目录
运行。回放失败或路径依赖源仓库时，状态为 `STAGING`。

### 12.4 来源 manifest、numeric provenance 和 release allowlist 三者必须闭合

每题必须有 `data/source_manifest.json`，至少包含：
`schema_version`、`task_id`、`fixture_classification`、`promotion_status`、
`supported_claims`、`unsupported_claims`、`required_next`。每个数值或标签在
`data/numeric_provenance.tsv` 中必须有来源、推导规则、状态和主张范围。

允许的状态只在语义正确时使用：`SOURCE_BOUND`、`DERIVED_SOURCE_BOUND`、
`CALIBRATION_EXCLUDED`、`CONTROL_PARAMETER`、`DECLARED_PARAMETER`、
`SOURCE_MISSING_BLOCKED`。后两种参数状态不能伪装成实验观察，
`SOURCE_MISSING_BLOCKED` 不能作为 release 科学证据。

`data/release_input_manifest.json.agent_visible_inputs` 必须明确列出
`data/source_manifest.json` 和 `data/numeric_provenance.tsv`，并且 allowlist 中的每个
文件在 `environment/` 中都存在。冻结清单、发布清单和实际文件的路径、字节数、SHA-256
不一致时直接 `FAIL`。没有真实来源闭环的题只能标为 `STAGING`。

### 12.5 agent 环境、测试环境和隐藏数据必须三向隔离

`environment/Dockerfile` 的 build context 是 `environment/`。必须检查：

- agent 可见输入完整复制到 `environment/data/`；若使用目录复制，必须递归复制整个
  `data`，不能漏掉 allowlist 中的策略文件；
- Dockerfile 不得 `COPY solution`、`verifier.py`、`tests/verification_data`、隐藏标签或
  参考答案；
- tests 镜像独立持有 verifier 和隐藏真值；
- `solution/`、`tests/`、隐藏目录不出现在 agent 镜像 build context 的可见路径中；
- `environment/data`、题包 `data` 和 `tests/verification_data` 的差异必须能由
  allowlist 和隐藏数据规则解释，不能出现无记录的数值漂移。

基础镜像必须是公开、固定版本的镜像；出现本机私有 `hsbf-codex-runtime` 或类似镜像名，
即使本机可以构建，也必须 `FAIL`。

### 12.6 指令协议必须做等价措辞和反例检查

对每个严格 schema 至少做一次人工或脚本化对抗检查：

- 正确同义词、错误枚举、漏填一列、改错一个键名分别运行；
- 每个要求独立的输出文件都必须单独完整，不能用“跨文件合计”满足单文件要求；
- 字面 token（例如 `yes`/`no`、`true`/`false`）必须在 agent 可见 instruction 或数据中
  原样出现；
- policy 键名与输出列名不同时必须给出显式映射；
- verifier 要求固定集合或固定行数时，必须写出集合成员和“恰好”行数，并明确禁止把
  trace/日志文件混入集合。

只通过 oracle、但没有 agent 冒烟或反例结果的题，不能据此判定 instruction 合格。

### 12.7 科学审阅是发布阻断项，不能自动生成通过结论

`author_private/scientific_review.json` 缺失、`status=pending`、缺少具名审阅人或缺少
逐条 claim 判断时，发布状态必须为 `STAGING`，`release_permitted=false`。脚本不得把
“pipeline 通过”“证据文件存在”自动改写成 `APPROVED`，也不得伪造 reviewer、日期或签名。

`experimental-design` 等只有方法和文献、没有真实观测快照的题，必须明确标记为
`DESIGN_FIXTURE_WITH_REAL_METHOD_REFERENCES` 或等价 staging 状态；文献引用不能替代
真实数据冻结。`pipeline_status`、`evidence_status`、`review_status` 必须分别记录，
不能用一个静态 PASS 覆盖另外两个缺口。

### 12.8 动态试跑前必须检查 Docker daemon 和网络边界

执行 Harbor 动态检查前先运行 `docker info`，并记录 Docker context、daemon 可用性和
镜像构建结果。若出现 socket 权限拒绝、daemon 不可用或镜像无法拉取，C1 必须记为
`EXECUTION_BLOCKED`；不能把历史 oracle 结果计作本包动态通过。

动态门禁必须分别验证：

- agent 构建阶段按需使用公开网络；
- agent 运行网络与 `task.toml` 的 `[environment].network_mode` 一致；
- verifier 运行时为 `no-network`；
- `test.sh` 不安装依赖、不下载数据、不调用外部服务；
- oracle reward 为 `1.0`，NOP 和关键字段 mutation 为 `0.0`。

Docker 不可用时可以完成静态审计，但最终包只能是 `STAGING`，不能写成“全门禁通过”。

### 12.9 打包、解包和 SHA-256 必须闭环

发布包必须从干净 staging 目录生成，排除 `jobs/`、`trials/`、`logs/`、缓存、
`.pytest_cache`、`__pycache__`、`.pyc`、`.DS_Store` 和临时文件。打包后必须：

1. 列出 tar 内容并统计 `task.toml`、Dockerfile、SOP 卡片和 README 数量；
2. 解压到新目录，重新运行静态门禁和 provenance/replay 检查；
3. 检查 SHA-256 sidecar 只引用最终包文件名，且校验值与最终压缩包一致；
4. 检查包内没有源仓库绝对路径、个人目录、旧版本残留或未声明文件；
5. 记录包的文件数、任务数、提交版本和生成时间。

任何“源目录通过、压缩包失败”或“sidecar 与包不一致”均为 `FAIL`，不能以源目录结果
覆盖交付包结果。

### 12.10 状态字段采用 fail-closed 语义

`PASS_LOCAL`、`STATIC_PASS`、`REPLAY_PASS` 只表示对应工程检查通过，不等价于可发布。
只有真实来源闭合、科学审阅批准、Docker 动态 oracle/NOP/mutation 通过、解包复核通过的
题目才能标为 `runnable` 并设置 `release_permitted=true`。任一条件缺失时：

```text
status = STAGING
release_permitted = false
```

检查报告必须分别列出通过项、阻断项、未执行项和执行环境；“未执行”不能折算为通过。

### 12.11 控制弃权比例，避免“弃权即最优”

仅有真实来源、冻结哈希和完整输出契约，不能证明题目能考察声明的全部科学能力。每个
科学考察项必须在 `claim_evidence_map.tsv` 或等价矩阵中标为以下一种：

- `POSITIVE_OBSERVABLE`：agent 可见真实数据支持至少一个可判定正例；
- `NEGATIVE_OBSERVABLE`：agent 可见真实数据支持至少一个可判定反例；
- `INSUFFICIENT_BY_DESIGN`：证据不足本身就是明确且主要的考察目标；
- `CONTROL_PARAMETER`：方法或教学控制参数，不得写成实验发现。

对混合分析题，弃权是合法答案的一部分，但必须是少数情况。默认发布门槛为：

- `abstain/hold/unknown/not_estimable` 的独立可评分样例占比不超过 **30%**；
- 这些样例对应的总分权重不超过 **25%**；
- blanket-abstain 变体的分数不得达到正确分析的 70%；
- 至少 70% 的分值来自需要读取和分析数据的 positive/negative observable 分支。

上述比例按独立科学判断或 query/contrast/replicate 单元计算，不按输出文件数量计算。
如果题目本来就是 metadata/evidence-boundary 审计，可以允许更高的弃权比例，但必须将
`task_scope` 标为 `boundary_only`，删除不可执行的广泛分析模块，且不能把它计入综合分析
题的能力覆盖率。

以下任一情况为 `FAIL` 或退回重构：

- 一个混合分析题有多个科学考察面，但 `INSUFFICIENT_BY_DESIGN` 超过 30%；
- 只提供 metadata，却要求图像、轨迹、谱图、guide-level 或 causal effect 结论；
- verifier 没有足够的 `POSITIVE_OBSERVABLE`/`NEGATIVE_OBSERVABLE` 分支，或 blanket
  `abstain/hold/unknown` 达到正确分析的 70%；
- 输出 artifact 很多，但新增的只是 trace、handoff 和格式文件，数据没有增加相应的
  独立科学判断；
- calibration/synthetic 数据支撑了大部分正确标签，而题面没有把它明确标成 calibration。

发布前必须对每个题运行四个变体并计算上述比例：

1. 全部 `abstain/hold/unknown`；
2. 对所有考察项强行给确定结论；
3. 正确回答一个可判定正例，同时对一个缺失证据分支弃权；
4. 把一个可判定正例改成错误的弃权。

第 3 种不必是唯一最高分，但第 1 种必须低于正确分析的 70%，第 4 种必须扣分，并且
混合分析题满足 30%/25% 弃权比例门槛。若题目是刻意的 metadata/evidence-boundary 审计题，
必须删去不可执行的 difficulty modules，并把题目标题、任务描述和评分目标限定为证据边界，
不能同时声称在测轨迹、图像、谱图或因果效应分析。

本门禁的逐题审计记录见仓库报告：
`reports/evidence_surface_abstention_audit_2026-09-24.md`。

每个题族的具体数据补齐、任务缩减、verifier 重标定和去向必须记录在：
`reports/per_task_repair_plans_2026-09-24.md`。修复计划不是科学审阅批准；计划完成后仍要
重新冻结来源、运行回放和动态 mutation。

### 12.12 每题必须有可执行的修复闭环

题目进入下一轮改造前，必须有一张逐题修复卡，至少包含：

- 当前最高版本和数据状态；
- 每个考察面的证据类型与文件路径；
- 需要补充的真实数据、许可、accession/DOI、版本和 SHA-256；
- 需要删除或缩小的不可执行考察面；
- 正例、反例、证据不足例和 blanket-abstain 的预期行为；
- verifier mutation、科学审阅、Docker 动态运行和打包复核的完成条件；
- 修复后的目标状态：`runnable`、`STAGING` 或 `CALIBRATION_ONLY`。

只有数据、任务描述、评分器和发布状态四者同时更新，修复卡才能标记完成。只新增
`source_manifest.json`、`README` 或 trace 文件而没有增加可判定科学证据，不算修复。


### 12.13 题目间差异和 tb-science 原题覆盖

#### 12.14.5 难度增加规则

难度应来自数据 join、统计单位、batch/replicate 结构、数值重算、排序、multiple-testing、source hash、sensitivity、decision predecessor chain、正负控和 mutation；不得通过增加无数据问题、让模型只能弃权、用 metadata 要求 spectrum/pixel/trajectory/causal effect，或用 trace 长度和最低轮次制造难度。

说明部分题目的有效工作阶段没有被题面明确要求。后续采用“有效工作量”而不是“人工最低轮数”
增加难度。每题必须在已有 artifact/trace 中留下三个独立阶段：

1. `inventory/provenance`：数据对象、统计单位、来源哈希、缺失字段、排除规则；
2. `primary recomputation`：至少两个从原始输入独立重算的数值、计数或排序；

### 12.15 全仓真实数据替换新增检查（2026-09-24）

本节记录 PBMC3k、ENCODE ATAC-seq 和 ComboSciPlex 替换合成夹具时新发现的通用问题。

#### 12.15.1 大型原始文件不得无审计地重复打包

原始 H5AD、矩阵或归档较大时，可以向 agent 提供确定性紧凑派生快照，但必须同时满足：

1. 登记官方 URL、accession、下载日期、原始字节数和原始 SHA-256；
2. 生成脚本在仓库内，记录精确字段、筛选、聚合、缺失值和排序规则；
3. 派生文件自身有 SHA-256，`source_freeze_manifest`、`release_input_manifest` 和
   `numeric_provenance` 三者一致；
4. verifier 从同一冻结派生输入独立重算，不能信任 agent 自报的汇总；
5. 原始文件没有进入 agent 镜像时，题目不得要求只有原始文件才支持的细胞级、基因级或
   因果结论。

检查失败时保持 `STAGING`。压缩原始文件重复复制到 solver、environment 和 tests 造成的
体积膨胀，也应视为打包缺陷。

#### 12.15.2 数据字段必须支持题名和 estimand

- 单细胞数据只有一个 cell line 时，不得把孔间复现性写成跨细胞系 transportability。
- 没有 dose 字段时，不得要求 dose-response 或剂量协同结论。
- 没有 ambient ground truth 或 cell-type labels 时，只能评价观测计数/marker retention，
  不得声称证明了 ambient removal efficacy 或完整 native-state preservation。
- ENCODE peak overlap 只能支持注册的区间重叠、排序和跨 context 预测；不能自动升级为因果
  regulatory activity。

每题的 `design_boundary.json` 或等价产物必须同时列出可计算项和不可识别项。不可识别项只占
小比例，不能替代对全部正向证据单元的计算。

#### 12.15.3 隐藏 target 必须与可解性兼容

transport/ranking 题可以把目标 context 留给独立 verifier，但 agent 的交付必须由可见来源
context 和公开注册的排序规则唯一决定。隐藏 target 只能做独立诊断或使用预先注册并经科学
审阅的阈值，不能要求 agent 猜测不可见标签。隐藏文件只进入 tests 镜像，agent 的
`environment/`、`solver/assets` 和 instruction 均不得泄露。

#### 12.15.4 最新题与历史版本必须分开审计

统计“当前可打包题目”时，每个题族只取最高语义版本；历史版本另列为 archive hygiene，不能
重复计题。发布前仍需扫描所有历史 Dockerfile，记录私有基础镜像和 `COPY solution`，但历史
缺陷不能误报成最新版本缺陷。报告至少同时给出：

- 最新题族数；
- 全部含 `task.toml` 的版本目录数；
- 最新版本静态问题数；
- 历史版本遗留问题数及是否会进入最终 tar allowlist。

#### 12.15.5 报告必须区分“缺文件”和“门禁待完成”

`evidence_grounding`、`source_freeze_manifest`、`numeric_provenance` 实际存在，但 scientific
review、license review 或 Oracle/NOP/mutation replay 尚未执行时，应报告“发布阻塞仍开放”，
不能写成“缺失 evidence/source/provenance”。至少分开统计：

```text
packages_missing_core_evidence
packages_with_open_release_blockers
```

这两个指标不能互相替代，也不能因为核心文件存在就自动标为 release-ready。

### 12.17 v14 结构化契约与科学区分度重构（2026-09-24）

v12-v14 的 30 次 trial 需要把失败机制与模型能力分开：大量 0 分来自 verifier 字面/结构误判，
而三轮中确认的模型侧实质科学错误只有 md-replica 一次。继续增加同义词或 trace 轮数不能提高
区分度，必须把答案从 instruction 移到真实数据和可审计的分析契约中。

七个高风险题（ambient、Perturb-seq、omics、experimental-design、CRISPR-screen、MD、
microscopy）必须同时提供 agent 可见的 `data/analysis_contract.json`、release manifest 条目和
environment 副本。契约必须声明统计单位、输入、三个独立阶段（`inventory_provenance`、
`primary_recomputation`、`adversarial_cross_check`）、正向证据单元、边界单元和
`blanket_abstention_is_invalid`。`check_data_sufficiency.py` 对这些字段 fail closed。

判分规则：

1. 难度来自真实数据 join、两个以上独立重算、donor/batch/replicate 结构、source hash、敏感性、正负控和跨 artifact 一致性；不以最低 tool-call 或最低轮数计分。
2. verifier 必须做结构化概念判断。同义词要求同句共现或等价集合关系，不能靠单个字面 token；decision predecessor 只验证 DAG 引用存在，不强制线性顺序。
3. Perturb-seq `mean_umi` 的分母是全部可见 cells；accepted/ambiguous 是独立 QC 计数。microscopy sensitivity 至少覆盖计划阈值集合中的两个阈值（不足两个时覆盖全部）。
4. metadata-only 题必须保留真实可计算的正向子集；不得用缺失 spectrum、pixel、完整 trajectory 或因果真值把整题退化为弃权。all-abstain、空输出和只写边界的 baseline 必须失败。

### 12.18 公开 processed metadata 的 schema 与最小下载检查（2026-09-24）

公开仓库中的 processed TSV/CSV 不能仅凭表头直接解析。GSE96583 的两个 processed TSV 实际每行
有 8 列，而表头只有 7 个字段：未命名的首列是 cell barcode。若直接使用普通 `DictReader`，
donor、condition、cell type 和 `singlet/doublet/ambs` 会整体错位，随后所有统计仍可能生成看似
合理但语义错误的结果。

新增强制检查：

1. 下载后先比较 header 列数、每行列数分布、首五行样例和每列主要取值；列数不一致时必须写出显式 schema 映射。
2. 对 donor、batch、condition、label 等关键字段检查唯一值、频数和允许集合；字段错位或出现坐标值时 fail closed。
3. 优先使用官方目录中的最小 processed 文件完成已注册 estimand；只有缺少必要变量时才下载大型原始归档。
4. source manifest 必须记录 accession、官方下载 URL、原文件 SHA-256、文件大小和解析规则；派生表还要记录转换脚本。
5. 同一真实来源可支持多题，但每题必须有不同 estimand、统计单位、输出 schema 和 mutation；共享数据本身不能证明题目差异性。
6. 真实标签中的 `ambs` 必须与 doublet 和 singlet 分开统计；不得把 ambiguous 默认为阴性或用整题弃权代替逐组边界判断。
7. 任何 processed label 只支持其已发布分析范围；demuxlet 标签可以用于标签率和分层审计，不能据此宣称新 expression-only classifier 已获验证。
