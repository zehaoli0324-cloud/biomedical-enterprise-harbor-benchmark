# Policy review package

This is a bounded planning decision, not experimental proof. The input bundle is intentionally nested and its field meanings are not restated here. Inspect `data/` recursively, discover the mission and operation catalog, and decide your own dependency-ordered workflow before interpreting records. Read the discovery manifest before interpreting records, reconstruct the relationship between policy records, the semantic lexicon, and the numeric rules, and do not use network access or parent directories.

Evaluate every policy record. Preserve the distinction between a clear proceed decision, an explicit human-review decision, an out-of-scope record, future-outcome leakage, and a numeric blocker. If proceed and review cues apply at the same time, do not resolve the ambiguity by choosing the higher utility; classify it for human review. Only an active, non-leaking, unambiguous, stable, in-budget record may be selected. If more than one record remains, select the highest replay utility and break exact ties by record ID. If none remains, select `human_review`.

Write the following artifacts under `outputs/`. The plan is part of the answer: it must contain each required operation exactly once, respect the discovered dependencies, stay within the discovered planning budget, declare `network_used=false`, and name the stop condition that justifies the final action. The verifier accepts any valid topological order and does not require a hidden canonical order. Do not add an operation merely to force a preferred decision.

- `outputs/plan.json`: a dependency-ordered workflow with `operations`, `total_cost`, `network_used=false`, and `stop_condition`.

- `outputs/plan.json`: a self-authored workflow plan with `operations`, `total_cost`, `network_used`, and `stop_condition`.

The output contract is semantic, but its equivalence rules are explicit. The verifier accepts either an ID-keyed `records` object or a list of record objects carrying `record_id`; `eligible` and `eligibility` are equivalent; status labels such as `clear_proceed`, `explicit_review`, `future_outcome` and `out_of_scope` are normalized to the declared statuses; blocker labels may include a specific prefix such as `numeric_blocker: uncertainty_above_maximum_for_proceed`; and discovery paths may consistently include or omit the `data/` prefix. These representations must not change the derived decision. `rules_version` remains required in `decision.json`, and `audit.md` must state the claim boundary in either the exact prose or the declared structured token form.

- `outputs/decision.json`: a JSON object with `selected_record` as the selected record ID string, `rules_version`, `claim_boundary` equal to `planning_only_not_experimental_proof`, `human_review_required` equal to `true`, and `records` as an object keyed by every record ID. Each value in `records` must contain exactly the derived `semantic_status`, `utility`, `utility_range`, `replay_count`, `eligible`, and `blocker_reasons`. Semantic statuses are `ambiguous`, `human_review`, `proceed`, or `unresolved`; an `unresolved` status is also accepted for a record that is explicitly blocked by `scope` or `future_outcome_leakage`. Blocker labels are `scope`, `semantic_ambiguity`, `future_outcome_leakage`, `signal_threshold`, `uncertainty`, `budget`, and `replay_stability`.
- `outputs/evidence.tsv`: one row for every policy record, with columns `record_id`, `semantic_status`, `utility`, `utility_range`, `replay_count`, `eligible`, and `blocker_reasons`. Use lowercase `true` or `false` for `eligible`.
- `outputs/discovery.json`: a JSON object with `discovered_files` as the sorted list of all file paths relative to `data/`, `input_hashes` as an object mapping those same relative paths to SHA-256 hashes, `network` copied from the discovery manifest, and `deterministic` equal to `true`.
- `outputs/audit.md`: explain how ambiguous language, scope, future outcomes, stability, budget, and human review affected the decision. It must contain the exact phrase `not experimental proof`.
